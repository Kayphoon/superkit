# 审核与冲突处理

知识写入后、相关代码交付前及提交/合并阶段主动审核，不等待人工提醒。只处理本次范围及受影响模块；没有知识变化时不制造 wiki 修改，自驱沉淀也不因缺少“记录”指令而被判定越权。

## 审核基准

“最新代码”指当前维护或交付版本的有效实现，不是时间戳较新的一方。明确本次范围和代码版本后再核验：

| 阶段 | 代码与知识的核对基准 |
|---|---|
| 日常维护 | 当前 checkout 的工作树 |
| 准备 commit | 实际会进入提交的完整内容，普通提交流程为完整 index |
| 审核已有提交 | 明确指定的 commit 内容 |
| 远端更新或合并完成 | 实际最终 merge/rebase 结果及本次目标分支 |

提交前可用 `git diff --cached --name-status` 定位范围，直接读取暂存版本及相关未变更文件。部分暂存以实际提交内容为准；未暂存代码、附件和 `git add -N` 占位不能补足缺失，首次没有 HEAD 也不例外。被审内容改变后重新审核，不复用旧结论。

目标分支从本次请求、已有 PR 上下文或仓库配置确定，不默猜；引用未刷新时只报告本地引用范围，不能声称已核对实时远端，也不擅自 fetch。rebase 可按已确认的当前重放步骤局部核验，但结束后须重新核对最终结果，中间状态不能作为最终通过。

## 知识冲突与功能归属

知识冲突永远以按上述基准确定的最新有效代码为准，不按 wiki 时间戳、作者、本地或远端身份选边，也不靠整文件 `ours` / `theirs` 覆盖。读取双方改动与共同祖先（存在时），逐条核实并自主合并仍成立的独有内容，纠正或移除已证实过时的现行说明，保留历史定位。Git 没有文本冲突或已清除标记，不代表语义一致。

与本次 commit feat 相关的知识更新到对应功能的 wiki 模块或章节，不按每个 commit 新建 wiki。目标分支尚无该功能，不否定本次代码中仍存在的实现；最终代码改变或移除该 feat 时，知识跟随更新。其它主题维持原归属，只做消除本次冲突或纠正已核实漂移所需的修改，不强塞进 feat wiki。

业务代码冲突未解或所需基准未定时，不能通过对应知识审核，也不能用 wiki 反过来裁决业务代码。在原任务授权内先确认代码结果；证据不足的差异保留，必要时按 [草稿生命周期](writing.md#草稿整理与清理) 记录。

## 双向核对

知识侧：新增或修改的结论有该版本的代码文件/符号依据，属于本次范围；未实现方案、其它任务发现或本机偶然状态不能写成既定事实。检查 [输出格式、引用和附件](writing.md#元数据与输出校验)，改名/合并不丢独有内容，正文不互相矛盾。

代码侧：按 diff 的语义选择受影响知识，核对函数、路径、配置和行为变化，不只依赖文本路径命中。本次改动使已有说明失效时同步更新；未影响已有知识时说明依据。使用中证实的旧错可以独立修正，不需要业务代码 diff，也不夹入无关的功能提交。范围外的新发现有价值时留本地草稿。

未核实或范围外的结论从本次正式编辑中移出或回到草稿；不覆盖别人、不自动回滚代码。修正后重新审核，未解决冲突、验证失败或证据不足的部分不能宣称通过。

## 交付与 Git 边界

回复或已授权的 PR 评审中简述审核范围/版本、代码依据、更新的 wiki 位置、格式/引用核对和语义结论及剩余缺口，不把审核过程另写成正式知识或维护日志。区分已编辑、已验证与已提交/合并；静态读码不能证明测试、真实引擎或界面已验收。

实际 Git 操作仍需原任务授权。获准提交时先界定范围和预检，仅暂存授权内容，对最终完整待提交快照审核后再 commit；index 已有其它任务内容时协调，不擅自移出或一起提交。不因维护或解冲突而丢弃未提交修改、重置代码、强推或擅自发布 PR。

## 可选独立审核

主线程按风险使用原生只读子代理复核，不作为每次写入的前置门禁。让其读取本 skill 和本审核协议，只提供项目路径、审核意图、必要源文件/附件、审核基准（工作树/index/具体提交）及合并时的目标 base，不整段转发用户会话；只读核验不承担知识检索服务。

在委派提示词中明确：不写 wiki 或 staging、不创建报告/临时文件、不执行 Git 写操作或修改配置、不联网或读取私有记忆、不再委派；仅返回有文件/符号证据的发现与未验证边界。主线程负责修正和复核，不注册新 agent、绑定模型或用外部进程替代。没有可用子代理可如实说明并自行审核；用户明确要求独立审核时不能静默替代。
